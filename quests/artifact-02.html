GiGo

Garbage In / Garbage Out. AI is a tool, not the author. Output is only useful when a human supplies context, understands the result, verifies it, and decides.

The central idea

Human thinking first.

Human → prompt → AI → output → verification → decision.

01
Human thinking

Define the task, audience, constraints, and what “good” would look like.

02

Give context instead of hoping the model invents it.

Keep, revise, or reject. The reviewer stays responsible.

Brief

What we were asked to do

Quest 2 had two parts. Part 1 asked each member to write a personal AI usage plan: how they intend to use AI tools during their studies, what responsible use looks like for them, and what GiGo means and how to avoid it.

Part 2 required a real context and a scenario card: a bad prompt and why it fails, a good prompt for the same task and why it is better, and a verification checklist.

Matthew used a technology-store website project. Elina documented a Java translation pipeline. Thijmen designed a bottle-cap identifier. There is no group PowerPoint for this quest; the documented scenarios are the artifact.

Our shared position

AI as a tool, not a shortcut

All three of us use AI in our studies — but with clear boundaries. We write our own thinking, check what AI gives us, and treat it as support rather than a replacement. The difference lies in how each of us applies that principle in practice.

Matthew

Technology store website

Prompt laboratory · university project context

A vague brief forces the model to invent a product. A specified brief forces a plan, an audit, and a human decision.

Bad input Fails

Build me a website about a tech store that sells tech media and generate a generous amount of revenue. Ensure the website is modern and follows web principles, integrating specific language suitable for sections related to the current project idea.

Why it fails

Vague requirements

“Modern” and “web principles” do not specify pages, users, or constraints.

Ambiguous language

“Suitable language” and “tech media” leave the model to guess the product.

No audience

Revenue is mentioned; students, consumers, and project limits are not.

No verification

Nothing tells the model — or the human — how to know the result is wrong.

Better input Plan first

Build a website for a technology store that sells technology products and related media. This is for a university project, so first understand the concept before implementing anything. The target audience should be students and general consumers interested in technology. First identify the purpose, target audience, website structure, required pages, content, visual style and main user journey. The website should be modern, responsive and follow good web design and accessibility principles. Do not immediately start implementing. First create a plan and explain any assumptions or missing information. After the plan, create an implementation plan and then build the website according to it. After implementation, audit the website against the original requirements, test the main functionality and identify anything that does not match the requirements. Do not assume that the result is correct just because the implementation works. Leave the final decision to the human reviewer.

This is better because it gives the AI information about the what, how, details, concept, goal, what to avoid and what to include. It also gives it a process to follow instead of expecting understanding from a short sentence.

Verification sequence

Mark items as reviewed. Checking a box does not replace the review; it records that the step was done.

Elina

Java translation pipeline

Architecture understanding · language support

A Java application that translates English sentences to Dutch through four modules. AI helped explain behaviour. Elina still had to understand and verify it.

Modules: model (data structures), analysis (syntactic tagging), translation (dictionary lookup), and rules (grammatical restructuring).

01
English input

The entry point receives an English text string from the user.

02
Sentence Analyzer

Parses the input into Token instances and assigns part-of-speech labels.

03
Token structure

The application displays the analyzed structure to the terminal.

04
Translator

References the loaded dictionary CSV to map each token to Dutch.

05
Dutch translation

The direct translation result is outputted for display.

06
Rule engine

The user picks a grammar rule; RuleEngine rearranges token sequence.

07
Final structure

The adjusted Dutch sentence is rendered as the ultimate output.

Where AI helped

  • Unknown words in Sentence Analyzer are given a default grammatical role such as “Other”, so the pipeline does not break.
  • Separating translation from syntax manipulation follows Single Responsibility: new grammar rules can be added without changing dictionary code.

What still had to be understood

  • Why unknown words can still pass through translation and rules without exceptions.
  • How modular design is applied in this specific architecture — used to write the summary, not to replace it.

Learning context

English is not Elina’s first language

AI can support language work: clarification, wording, understanding, and confidence while studying in English. That support is not a substitute for judgement. The documented interactions above are about the Java pipeline — understanding a module and verifying an explanation — not about handing the project to a model.

Thijmen

Bottle cap identifier

Programming context · C++ / C# learning

Ten years of collecting, more than 300 unique caps, and a need to catalogue them. The prompt work sits inside a wider learning path: unfamiliar syntax, debugging, and human checks.

Illustrative representation

No original screenshot of Thijmen’s codebase is in the repository. The diagram below is a designed placeholder for that learning context — not student evidence.

Learning context — C++ experience, C# study, AI as a support mechanism.

Bad input Too generic

How can I make a bottle cap identifier

Better input Context + constraints

I am making a bottle cap identifier, it will need to scan the caps, store their picture somewhere and be able to compare the scanned caps with newly scanned caps from anywhere to check whether the cap is unique or not, what can I use to scan them, store them, compare them, run it 24/7 and access it from anywhere outside of my local network

The short prompt fails because it is generic: zero context and no expectations. The longer prompt succeeds because it states instructions, expectations and context.

Verification

Go to the Google/GitHub pages of the listed systems and check if they match what was asked for and whether they can be used (no blocking licence or technical complication). If they do, ask for more specifics and repeat until the setup is clear. If they don’t, explain what is wrong and ask for another way.

Boundary

What AI did vs what we did

What AI did

  • Drafted options from a prompt.
  • Explained module behaviour in the Java pipeline.
  • Listed candidate systems for the identifier.

What we did

  • Chose a real context and wrote the scenario.
  • Judged whether an explanation fitted the actual code.
  • Verified claims against sources and kept the decision.
Reflection

When AI is useful, and when it is not

AI is useful when the human provides adequate context, understands the result, verifies it and decides what to do with it.

AI becomes harmful when vague input is treated as a finished brief, or when a fluent answer is mistaken for a checked one. GiGo is not a slogan. It is the failure mode of this quest.
