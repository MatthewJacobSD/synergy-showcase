Artifact 02

GiGo — Garbage In / Garbage Out

Using AI tools responsibly and documenting that use properly. This artifact explores how the quality of AI output depends on the quality of the input, and how prompt design determines whether you get useful results or garbage.

Quest 2 — Usage of AI
Status Completed
Members Matthew, Elina, Thijmen

What we were asked to do

Quest 2 had two parts. Part 1 asked each member to write a personal AI usage plan: how they intend to use AI tools during their studies, what responsible use looks like for them, and what GiGo (Garbage In, Garbage Out) means and how to avoid it.

Part 2 required choosing a real context from studies or daily life and writing a scenario card that includes a bad prompt and why it fails, a good prompt for the same task and why it is better, and a verification checklist — steps to check whether the output is reliable.

Our approach

Each member chose their own real-world context for the prompt scenario. Matthew used a technology store website project, Elina explored a Java translation pipeline, and Thijmen designed a bottle cap identifier system. We then combined our individual work into a single PowerPoint presentation.

Individual contributions

Matthew Jacob Sarkodie Darkwah

Scenario: Technology Store Website

Bad Prompt

"Build me a website about a tech store that sells tech media and generate a generous amount of revenue. Ensure the website is modern and follows web principles, integrating specific language suitable for sections related to the current project idea."

The main problem is that it does not give enough specific information. Words such as "modern", "web principles" and "suitable language" can mean different things depending on the project. The AI has to make its own assumptions, which can lead to a result that does not match the original idea.

Good Prompt

"Build a website for a technology store that sells technology products and related media. This is for a university project, so first understand the concept before implementing anything. The target audience should be students and general consumers interested in technology. First identify the purpose, target audience, website structure, required pages, content, visual style and main user journey. The website should be modern, responsive and follow good web design and accessibility principles. Do not immediately start implementing. First create a plan and explain any assumptions or missing information. After the plan, create an implementation plan and then build the website according to it. After implementation, audit the website against the original requirements, test the main functionality and identify anything that does not match the requirements. Do not assume that the result is correct just because the implementation works. Leave the final decision to the human reviewer."

This is better because it gives the AI more information about the what, how, details, concept, goal, what to avoid and what to include instead of expecting it to understand everything from a short sentence. It also gives it a process to follow.

Verification Checklist

  • Does it follow the original idea? Compare the result with what was originally wanted.
  • Does it follow the requirements? Check that required pages, sections and functionality are there.
  • Is the content correct? Check whether the AI has invented information or misunderstood something.
  • Does the design make sense? Check layout, navigation, typography, images and consistency.
  • Does it work on different screens? Test desktop, tablet and mobile.
  • Does the functionality work? Manually test buttons, navigation, forms and other important parts.
  • Check the code. Inspect for obvious errors, unnecessary code, duplicated code.
  • Human verification. Personally review the result instead of assuming the AI is correct.
  • Give the AI feedback and test again. If something is wrong, explain and ask for refinement.
  • Human decision. Decide whether the result is good enough to continue with.

Elina Nilisani

Scenario: Java Translation Pipeline

The Project

A Java application that translates English sentences to Dutch through four modules: model (data structures), analysis (syntactic tagging), translation (dictionary lookup), and rules (grammatical restructuring).

How a Sentence Travels Through the System

  1. The entry point receives an English text string from the user.
  2. Sentence Analyzer parses the input into Token instances and assigns part-of-speech labels.
  3. The application displays the analyzed structure to the terminal.
  4. Translator references the loaded dictionary CSV to map each token to its Dutch translation.
  5. The direct translation result is outputted for display.
  6. The user picks a specific grammar rule option from the console prompt.
  7. RuleEngine processes the tokens according to the selected rule and rearranges their sequence.
  8. The adjusted final Dutch sentence structure is rendered as the ultimate output.

AI Interaction 1

What I needed: Clarify how Sentence Analyzer handles words missing from the analysis CSV lookup files.

What AI told me: Unlisted words are given a default or generic grammatical role (like 'Other') so the pipeline doesn't break.

What I did with it: Noted this behavior to understand why unknown words can still pass through the translation and rule pipeline without throwing exceptions.

AI Interaction 2

What I needed: Understand the design reason behind separating translation logic from syntax manipulation logic.

What AI told me: Keeping them separate follows the Single Responsibility Principle, making it easier to add new grammar rules without altering the dictionary translation code.

What I did with it: Used this insight to write the summary of the architecture and better grasp how modular design is applied.

Thijmen Verschuur

Scenario: Bottle Cap Identifier

Context

Collecting bottle caps for over 10 years with over 300 unique ones, but starting to lose track of which ones are in the collection. Working on a better way to catalogue and identify them.

Bad Prompt

"How can I make a bottle cap identifier"

Fails because it is way too generic, there is zero context behind it and no clear expectations.

Good Prompt

"I am making a bottle cap identifier, it will need to scan the caps, store their picture somewhere and be able to compare the scanned caps with newly scanned caps from anywhere to check whether the can is unique or not, what can I use to scan them, store them, compare them, run it 24/7 and access it from anywhere outside of my local network"

Succeeds because it has very clear instructions, expectations and context.

Verification Checklist

Go to the Google/GitHub pages of the listed systems and check if this matches what was asked for and if it can be used (no specific licensing or technical complications). If they do, go back and ask for more info on the specifics and repeat until there is a clear setup. If they don't, explain what's wrong with them and ask to find another way.
